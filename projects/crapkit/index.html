crapkit

Know where the code needs attention.

crapkit brings complexity, test coverage and change history together to help developers and coding agents decide what to improve next.

The problem

Where should the next
hour of work go?

Code can be easy to generate and hard to change with confidence. A passing test suite or a repository-wide coverage percentage does not tell you which functions combine complicated logic with gaps in testing.

I created crapkit to make that work visible at the function level, and to make the same evidence usable by people, coding agents and automated checks.

01

Measure the function

Combine cyclomatic complexity with test coverage using the existing CRAP metric. Where coverage is unavailable, show complexity on its own rather than imply that testing was measured.

02

Choose the next change

Use change history to rank the work. A complicated function that changes often deserves a different level of attention from code that rarely moves.

03

Keep progress from slipping

Record existing debt as a baseline, then check changes against it. The ratchet allows recorded scores to improve but prevents them from rising.

Built for the way teams work.

Use it from the command line, connect a coding agent through MCP, or run it in a GitHub Actions workflow. Analysis and scoring run locally without telemetry; configured test and other commands retain their own behavior.

The metric and the tool

The CRAP metric predates crapkit. My work is the tooling around measurement, prioritization and change checks. These signals help guide review; they do not establish that software is correct.

Reading the measurements

Coverage is measured within each function: branch coverage when branches exist, otherwise line coverage. CRAP combines that coverage fraction with cyclomatic complexity. With full measured coverage, the score equals the complexity; adding tests did not simplify the code.

The reported total is the sum of the eight function scores, which crapkit calls crap_load. It is not an estimate of hours saved or the number of tests needed. The target of 6 is this example’s configured threshold. Values in the table are rounded; the CSV retains the measured precision.

The CRAP metric was introduced by Alberto Savoia and Bob Evans in 2007. My contribution is crapkit’s tooling around measurement and change checks.

What this does—and does not—show

This is a teaching illustration, not a production benchmark, a refactoring result or evidence of fewer defects or higher productivity. The deliberately small fixture makes the mechanism inspectable. High coverage alone does not establish that assertions are strong or the program is correct.

Reproduce the result

Download and extract the package, then choose a fresh Python 3.11+ environment with Git available. Install the supplied pinned requirements in that environment and run the reproduction script. The README includes Windows and macOS/Linux commands.

python -m pip install -r requirements-reproduce.txt
python reproduce.py --output results

The runner installs nothing and refuses an existing output directory. It runs the bundled public fixture, adds the supplied tests, and compares the measured result with the published values.
