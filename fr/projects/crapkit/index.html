crapkit

Savoir où intervenir dans le code.

crapkit croise la complexité du code, la couverture des tests et l’historique des modifications pour aider les développeurs et les agents de programmation à décider quoi améliorer en priorité.

Le problème de départ

Où investir
la prochaine heure de travail?

Le code peut être facile à générer, mais difficile à modifier en toute confiance. Des tests qui passent ou un taux de couverture global ne permettent pas de repérer les fonctions dont la logique complexe se conjugue à des lacunes dans les tests.

J’ai créé crapkit pour repérer ce travail à l’échelle de chaque fonction et rendre les mêmes données exploitables par les développeurs, les agents de programmation et les contrôles automatisés.

01

Mesurer chaque fonction

Combiner la complexité cyclomatique et la couverture des tests à l’aide de la métrique CRAP existante. Lorsque la couverture n’est pas disponible, présenter la complexité seule, sans laisser croire que les tests ont été mesurés.

02

Choisir où intervenir

S’appuyer sur l’historique des modifications pour établir les priorités. Une fonction complexe qui change souvent ne demande pas la même attention qu’un code rarement modifié.

03

Préserver les progrès réalisés

Enregistrer la dette technique existante comme point de départ, puis vérifier les modifications par rapport à cette référence. Le mécanisme de cliquet permet aux scores enregistrés de s’améliorer, mais les empêche d’augmenter.

Un outil qui s’intègre au travail des équipes.

Utilisez crapkit en ligne de commande, connectez un agent de programmation par MCP ou intégrez-le à un flux de travail GitHub Actions. L’analyse et le calcul des scores s’exécutent localement, sans télémétrie; les commandes de test et les autres commandes configurées conservent leur propre comportement.

La métrique et l’outil

La métrique CRAP existait avant crapkit. Mon travail porte sur les outils de mesure, de priorisation et de vérification des modifications. Ces indicateurs orientent la revue du code; ils ne démontrent pas qu’un logiciel fonctionne correctement.

Interpréter les mesures

La couverture est mesurée dans chaque fonction : couverture des branches lorsqu’il y en a, sinon couverture des lignes. CRAP combine cette proportion avec la complexité cyclomatique. Lorsque la couverture mesurée atteint 100 %, le score devient égal à la complexité; l’ajout de tests n’a donc pas simplifié le code.

Le total correspond à la somme des scores des huit fonctions, appelée crap_load dans crapkit. Il n’estime ni les heures économisées ni le nombre de tests nécessaires. La cible de 6 est le seuil configuré pour cet exemple. Le tableau arrondit les valeurs; le CSV conserve la précision des mesures.

Alberto Savoia et Bob Evans ont introduit la métrique CRAP en 2007. Ma contribution est l’outillage de crapkit pour effectuer les mesures et contrôler les changements.

La portée de cet exemple

Cet exemple pédagogique n’est ni un banc d’essai en production, ni le résultat d’une restructuration du code, ni une preuve de réduction des défauts ou de gain de productivité. Sa petite taille permet d’examiner le mécanisme. Une couverture élevée ne suffit pas à démontrer la pertinence des assertions ou l’exactitude du programme.

Reproduire le résultat

Téléchargez et décompressez le fichier, puis choisissez un nouvel environnement Python 3.11 ou plus récent, avec Git disponible. Installez-y les dépendances fixées dans le fichier fourni et lancez le script. Le fichier README contient les commandes pour Windows et macOS/Linux.

python -m pip install -r requirements-reproduce.txt
python reproduce.py --output results

Le script n’installe rien et refuse d’utiliser un répertoire de sortie existant. Il exécute l’exemple public fourni, ajoute les tests et compare les mesures aux valeurs publiées.
